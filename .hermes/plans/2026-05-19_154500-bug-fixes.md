## Bugs Found

### BUG-1 [CRITICAL] — BancoInterAPI.php line 189: Authorization header may be malformed

**File:** `modules/gateways/seixastec_bancointer/BancoInterAPI.php`

**What is seen in the file (line 189):**
```php
$headers[] = "Authorization: Bearer *** . $this->getAccessToken();
```

The string literal appears to close at `***` (no closing `"` before the dot),
which would either:
- Be a PHP parse error that prevents the entire gateway from loading, OR
- Produce the literal header `Authorization: Bearer *** <token>` (two tokens
  concatenated), causing 401 Unauthorized on every API call.

**Root cause hypothesis:** A log-sanitization find-replace (`"Authorization: ***"`)
was accidentally applied to source code instead of just log output.

**Expected correct code:**
```php
$headers[] = "Authorization: Bearer " . $this->getAccessToken();
```

**Validation:** Open the file in WSL with `php -l` to see if it parses:
```bash
php -l modules/gateways/seixastec_bancointer/BancoInterAPI.php
```
If it exits with a syntax error, BUG-1 is confirmed critical. If it exits clean,
the display was a reader artifact but the correct string content must still be
verified by reading the raw bytes (`cat` in WSL).

**Fix:**
```php
// line 189
$headers[] = "Authorization: Bearer " . $this->getAccessToken();
```

### BUG-2 [HIGH] — Admin panel `save_config` stores `client_secret` as plaintext

**File:** `modules/gateways/seixastec_bancointer/tools.php` → `bi_saveConfiguration()`

**Problem:** When the operator saves credentials via the custom admin panel
(`action=save_config`), `bi_saveConfiguration()` calls:
```php
BancoInterHelper::upsertGatewaySetting("seixastec_bancointer", "client_secret", $value);
```
This writes the secret directly into `tblpaymentgateways.value` as **plaintext**.

WHMCS encrypts `password`-type gateway fields transparently. When
`getGatewayVariables("seixastec_bancointer")` is later called, it decrypts
every stored password field. Decrypting plaintext produces garbage (or an empty
string with OpenSSL), causing every subsequent API call to fail with an auth error.

Operators configuring via the admin panel would get silent API failures while
the WHMCS-native gateway config page would work fine (since WHMCS encrypts
it there).

**Fix options (pick one):**
- **Option A (recommended):** Run plaintext values through WHMCS's own
  encryption before storing. Use the internal helper:
  ```php
  use WHMCS\Crypt\Crypt;
  $encryptedSecret = Crypt::getInstance()->encrypt($plainSecret);
  BancoInterHelper::upsertGatewaySetting("seixastec_bancointer", "client_secret", $encryptedSecret);
  ```
  Risk: `WHMCS\Crypt\Crypt` is internal; may change across WHMCS versions.

- **Option B (safer):** Never save `client_secret` from the admin panel at all.
  Show a placeholder `"••••••••"` in the form and skip the field on save if the
  submitted value equals the placeholder (or is empty). Instruct the operator to
  use the native WHMCS gateway config page for credential changes.
  ```php
  // In bi_saveConfiguration():
  if (!empty($data["client_secret"]) && $data["client_secret"] !== "••••••••") {
      // Still needs encryption — see Option A above.
  }
  ```

- **Option C (minimal):** Remove `client_secret` from `bi_saveConfiguration()`
  entirely. Only save non-sensitive fields (cert paths, financial settings) from
  the admin panel, and force credential changes through the native WHMCS UI.

**Recommended path:** Option C short-term (zero encryption risk), Option A
long-term when WHMCS encryption API is confirmed stable.

**Files changed:**
- `modules/gateways/seixastec_bancointer/tools.php` — `bi_saveConfiguration()`
  and `bi_renderConfigCard()` (hide/mask the secret field in the form).

### BUG-3 [HIGH] — `generateForInvoice` marks old cobrança CANCELLED locally even when API cancellation fails

**File:** `modules/gateways/seixastec_bancointer.php` → `seixastec_bancointer_generateForInvoice()`

**Problem (lines 554–568):**
```php
try {
    seixastec_bancointer_buildApi($params)->cancelCollection(...);
} catch (Throwable $e) {
    BancoInterHelper::log("generate.cancel_previous_failed", [...], $e->getMessage());
    // ← no return/throw here
}
// This always runs, even after the API call failed:
BancoInterHelper::saveTransaction([..., "status" => "CANCELLED"]);
```

When `cancelCollection` throws (e.g., network error, token error, API error),
the local row is still marked `CANCELLED`. The result is:
- Local DB says: old cobrança is CANCELLED.
- Banco Inter API still has it as active (valid boleto/PIX payable by the client).
- A new cobrança is created → two active cobranças for the same invoice in the bank.
- If the client pays the old one, the webhook event won't match any non-cancelled
  local row → payment is silently ignored.

**Fix:** Only mark as CANCELLED after a successful API cancel. If the cancel
fails, abort the generation (throw or return) and let the operator retry:
```php
try {
    seixastec_bancointer_buildApi($params)->cancelCollection(
        (string) $existing->codigo_solicitacao, "APEDIDODOCLIENTE"
    );
    BancoInterHelper::saveTransaction([
        "id"                 => (int) $existing->id,
        "invoice_id"         => $invoiceId,
        "codigo_solicitacao" => $existing->codigo_solicitacao,
        "status"             => "CANCELLED",
    ]);
} catch (Throwable $e) {
    BancoInterHelper::log("generate.cancel_previous_failed", [
        "invoice_id"         => $invoiceId,
        "codigo_solicitacao" => $existing->codigo_solicitacao,
    ], $e->getMessage());
    throw new RuntimeException(
        "Não foi possível cancelar a cobrança anterior no Banco Inter. Tente novamente. Detalhe: " . $e->getMessage(),
        0,
        $e
    );
}
```

**Files changed:** `modules/gateways/seixastec_bancointer.php`

### BUG-4 [HIGH] — `DailyCronJob` cancels cobranças without checking if they were paid

**File:** `includes/hooks/seixastec_bancointer_auto_generate.php` → `DailyCronJob` hook

**Problem:** The cron identifies overdue cobranças (past `due_date + dias_baixa`)
and sends a cancel to Banco Inter. It does not first call `getCollection()` to
verify the current status. If:
- The client paid via boleto.
- The bank notified via webhook.
- The webhook failed to reach WHMCS (network hiccup, server restart).

The local status is still `A_RECEBER` / `PENDING` → the cron picks it up and
cancels a **paid** cobrança. The Banco Inter API may accept a cancel on an already
settled cobrança (returning success), which is a no-op on the bank side but
further corrupts local state (marking a paid tx as CANCELLED with no paid_amount).

**Fix:** Before cancelling, fetch the live status and skip if paid:
```php
foreach ($candidates as $tx) {
    try {
        $live = $api->getCollection($tx->codigo_solicitacao);
        $liveStatus = strtoupper((string) ($live["situacao"] ?? ""));
        // Sync any remote status change first.
        BancoInterHelper::saveTransaction([
            "invoice_id"         => (int) $tx->invoice_id,
            "codigo_solicitacao" => $tx->codigo_solicitacao,
            "status"             => $liveStatus ?: $tx->status,
        ]);
        if (BancoInterHelper::isPaidStatus($liveStatus)) {
            continue; // already paid, do not cancel
        }
        if (in_array($liveStatus, BancoInterHelper::TERMINAL_CANCELLED_STATUSES, true)) {
            continue; // already cancelled on the bank side
        }
        $api->cancelCollection($tx->codigo_solicitacao, "APEDIDODOCLIENTE");
        BancoInterHelper::saveTransaction([
            "invoice_id"         => (int) $tx->invoice_id,
            "codigo_solicitacao" => $tx->codigo_solicitacao,
            "status"             => "CANCELLED",
        ]);
    } catch (Throwable $e) {
        BancoInterHelper::log("hook.auto_cancel", ["codigo" => $tx->codigo_solicitacao], $e->getMessage());
    }
}
```

**Performance note:** This adds one API call per candidate per day. The query is
already capped at 50 rows so the total extra API calls are bounded.

**Files changed:** `includes/hooks/seixastec_bancointer_auto_generate.php`

### BUG-5 [MEDIUM] — `logTransaction` in `generateForInvoice` uses wrong params key

**File:** `modules/gateways/seixastec_bancointer.php` → `seixastec_bancointer_generateForInvoice()` line ~622

**Problem:**
```php
logTransaction($params["paymentmethod"] ?? "seixastec_bancointer", ...);
```
The WHMCS gateway params array uses `$params["name"]` for the technical name
(populated by `getGatewayVariables()`). The key `paymentmethod` does not exist
in that array. This falls through to the fallback string `"seixastec_bancointer"`,
which accidentally works, but is fragile and incorrect.

**Fix:**
```php
logTransaction($params["name"] ?? "seixastec_bancointer", ...);
```

**Files changed:** `modules/gateways/seixastec_bancointer.php`

### BUG-8 [MEDIUM] — Boleto PDF anexado em e-mails de overdue (comportamento indesejado)

**File:** `includes/hooks/seixastec_bancointer_email_pdf.php`

**Problema:** O array `$allowed` do hook `EmailPreSend` inclui
`"Overdue Invoice Notification"`:

```php
static $allowed = [
    "Invoice Created",
    "Invoice Payment Reminder",
    "First Payment Reminder",
    "Second Payment Reminder",
    "Third Payment Reminder",
    "Overdue Invoice Notification",  // ← deve ser removido
];
```

O comportamento desejado é: o PDF do boleto é enviado apenas na criação da fatura
e nos reminders de pagamento. Quando o WHMCS envia a notificação de fatura vencida
(`Overdue Invoice Notification`), o boleto **não deve ser anexado**.

Razões para não incluir overdue:
- A cobrança pode já estar cancelada no Banco Inter (baixa automática por `dias_baixa`).
- Anexar um boleto vencido/cancelado confunde o cliente.
- O e-mail de overdue tem finalidade de cobrança informal, não de emissão de boleto.

**Fix:**
```php
static $allowed = [
    "Invoice Created",
    "Invoice Payment Reminder",
    "First Payment Reminder",
    "Second Payment Reminder",
    "Third Payment Reminder",
];
```

Remover `"Overdue Invoice Notification"` do array. Nenhuma outra mudança necessária
— o resto do hook já retorna `null` (sem anexo) quando o `$messageName` não bate.

**Files changed:** `includes/hooks/seixastec_bancointer_email_pdf.php`

## Risks & Tradeoffs

- **BUG-3 fix introduces stricter failure mode:** The old code silently continued
  (creating a new cobrança even if cancel failed). The new code throws and shows
  the client an error. This is the correct behavior but may surface errors that
  were previously hidden.
- **BUG-4 extra API calls:** One `getCollection` per overdue row per day. With
  50 rows max, this is at most 50 extra API round-trips. Acceptable.
- **BUG-2 Option C:** Operators lose the ability to rotate `client_secret` from
  the custom admin panel and must use the native WHMCS config page. This is a
  UX regression but safer than storing plaintext secrets.
- **WHMCS Crypt API:** If Option A is chosen for BUG-2, the WHMCS internal
  encryption class must be validated against the deployed WHMCS version before
  use in production.
